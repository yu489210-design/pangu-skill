# 盘古 Skill

第一版是 instruction-only Skill。详细架构依据来自 `references/architecture.md`。

## Purpose

盘古 Skill 的目标是帮助用户制作一个具体对象、作品、产品或项目实例。用户调用本 Skill 时，表面目标不是制作 Skill，而是获得属于自己的成品实例。

Skill 生成只是内部中间过程：先生成高质量范式实例，再抽象临时专用 Skill，再生成用户个性化实例。这个过程用于稳定质量和结构，不把临时 Skill 文档当作默认交付。

输出重点始终是用户最终想要的实例。只有用户明确询问生成逻辑或后续复用时，才说明内部方法摘要或升级可能。

## When to use this skill

当用户表达想制作、设计、生成、搭建、规划一个具体东西时，使用本 Skill。典型请求包括把模糊想法变成可执行成品方案，或制作作品、项目、工具、内容、资源包、品牌方案、学习资料、实验报告、网页工具、游戏资源等。

即使用户没有明确说要做 Skill，只要他说“我想做一个……”“帮我设计一个……”“生成一个能用的……”“从零做一个……”，也应按盘古 Skill 的实例生成路径处理。

不要在用户只是闲聊、解释概念、翻译、简单问答，或只要求总结一段已有文本时使用本 Skill。用户明确只要普通回答，而不是制作具体实例时，也不要启动盘古路径。

如果用户明确要求制作一个独立 Skill，按普通 Skill 制作需求处理；除非他明确要用盘古机制来生成实例，否则不要把它混淆为盘古 Skill 的默认路径。

## Core operating principle

不要直接从用户需求跳到成品。先建立该类对象的高质量范式，再从范式生产过程抽象出临时专用 Skill，最后调用该临时 Skill 生成用户个性化实例。

三层分工必须保持清楚：第一层真实生产一个高质量普遍实例，并留下关键节点交互轨迹；第二层把轨迹抽象成可复用的方法链，形成临时专用 Skill；第三层把用户需求调节成可执行参数，并调用临时专用 Skill 生成用户实例。

临时 Skill 是内部中间产物，不是默认交付物。除非用户明确询问生成逻辑或要求后续复用，不要把临时 Skill 文档展示为结果。

默认把用户最终想要的具体实例作为交付重点。不要把回答变成三层过程解释、内部方法说明或临时 Skill 展示。

当用户需求模糊时，先判断哪些信息可以用高质量范式默认补全。只有缺失信息会影响方向、结构、质量或交付形态时，才提出少量关键追问。

当用户需求过多或互相冲突时，先做需求分层、冲突检测和主线收束。不要机械照单全收；把硬约束、核心偏好和弱偏好整理成可执行实例方向。

## Layer 1: Produce a high-quality paradigm instance

第一层先生产一个高质量普遍实例。这里的“普遍”指能作为同类对象的质量范式和结构参照，不是普通、平均或模板化实例；不要直接生产用户最终实例，也不要只列一份空泛流程。

接收到用户目标后，先生成与目标对象高度匹配的领域造物专家。专家必须具体到对象类别和真实制作职责，是推动产品成型的造物专家，不是只提供建议的顾问。

专家定位要随对象变化而变化：制作 Minecraft 材质包时，应是 Minecraft Java 版资源包视觉设计师与资源包工程师；制作短视频账号时，应是短视频账号定位策划师与内容增长专家；制作网页工具时，应是产品经理、前端工程师与交互设计师组成的造物专家组。

专家开始生产高质量普遍实例之前，必须先建立当前项目的专家证据链。专家不能只声明自己是专家，而要说明该领域必须参考的原版、行业标准、成熟案例或平台规则；哪些判断不能凭想象完成；哪些对象必须通过实际场景、渲染环境、运行环境或用户操作来验证；哪些质量标准必须先定义，后生成。

专家还必须先识别当前项目的高风险节点。高风险节点是指一旦错误会显著影响最终体验，不能只靠静态文本或预览判断，会受到平台、渲染、运行环境、用户操作、文件格式、版本兼容或现实约束影响，并且后续批量生产会放大错误的节点。

对于高风险节点，专家不得直接批量生成。必须先做最小原型、样张、局部验证或场景验证；只有验证通过后，才允许进入大范围生产。

例如制作 Minecraft PvP 材质包时，弓朝向、`bow_pulling_0/1/2`、第一人称手持效果、短剑长度、低火高度、羊毛辨识度、药水辨识度、粒子干扰程度、像素材质硬边规则都属于需要参照或验证的高风险内容。不能只看 PNG 预览，也不能把普通图片的平滑放大当成 PvP 像素材质的高清优化。

专家最重要的能力是关键节点感：识别项目从想法到成品过程中，哪些制作节点真正决定结构、质量、后续制作和交付结果。

关键节点不是普通步骤，而是会改变项目状态、影响后续质量、决定最终交付形态的制作决策点。“打开软件”“开始制作”“进行优化”这类动作不是关键节点；“确定风格母体”“建立结构骨架”“确定核心功能闭环”“建立文件结构”“制定质量验收标准”这类动作才是关键节点。

v0.2 后，第一层执行顺序是：生成领域造物专家 → 建立专家证据链 → 识别高风险节点 → 对高风险节点做最小验证 → 通过关键节点式交互生产高质量普遍实例 → 固化节点成果和验证结果 → 产出高质量普遍实例和关键节点交互轨迹。

专家生产高质量普遍实例时，不得先机械列出完整节点清单再开始制作。核心节点必须在真实制作推进过程中自然产生，并随产品成型状态被识别和处理。

专家每一次与 AI 的交互都必须发生在当前关键制作节点上。每次交互都要短、准、必要，只解决一个关键问题，并产出能推动产品继续成型的节点成果。

每个节点交互完成后，专家必须验收并固化节点成果。每个节点至少保留：当前节点、本次交互解决的问题、AI 产出、专家采纳结果、对后续制作的影响。第一层留下的节点轨迹还要记录证据链依据、高风险节点、验证方式、验证结果，以及哪些内容因此被允许批量生成。

第一层结束时，必须产出两个结果：一个高质量普遍实例，以及一条关键节点交互轨迹。第一层输出主要用于后续抽象临时专用 Skill，不要把节点轨迹当作用户默认交付物。

## Layer 2: Compile the process into a temporary specialized skill

第二层的目标是把第一层真实制作高质量普遍实例时留下的关键节点交互轨迹，抽象成一个针对当前对象类别的临时专用 Skill。

第二层不得重新制作产品，也不得重新凭空规划流程。它只能从第一层的真实节点轨迹中提炼方法，不能脱离轨迹自由发挥。

核心路径是：关键节点交互轨迹 → 节点方法 → 方法链 → 临时专用 Skill。

v0.2 后，关键节点交互轨迹不仅包括生产节点，也包括证据链节点和验证节点。第二层不能只抽象“如何生成内容”，还必须抽象“生成前需要哪些证据”和“哪些高风险内容必须先验证”。

如果第一层建立了原版参照、行业标准、成熟案例、平台规则或运行环境基准，第二层必须将这些内容抽象成临时专用 Skill 的前置证据链方法。例如制作 Minecraft PvP 材质包时，不能只包含“生成弓贴图”方法，还必须包含“确认原版弓贴图方向和第一人称渲染基准”的方法；制作网页工具时，不能只包含“生成页面”方法，还必须包含“确认数据保存方式、刷新后持久化和异常输入处理”的方法；制作实验报告时，不能只包含“生成报告段落”方法，还必须包含“确认是否有原始数据，缺失数据时不得编造”的方法。

把每一次关键节点交互转化为一个可复用的节点方法。节点方法不是复述原对话，而是提炼该节点背后的可复用创造动作。

每个节点方法必须包含：方法名、来源节点、适用场景、输入信息、处理动作、输出结果、默认策略、质量标准、后续影响。

如果第一层识别了高风险节点，并做了最小原型、样张、局部验证或场景验证，第二层必须将这些验证动作抽象成临时专用 Skill 的质量闸门。验证节点不能被简化成普通“优化”或“检查”，必须说明需要验证什么、为什么高风险、通过什么环境或标准验证、通过后允许进入哪些后续批量生成、不通过时应回到哪个方法节点修正。

把节点方法串联成方法链。串联依据必须来自第一层真实制作过程中的顺序、依赖关系和质量约束，而不是简单按表面步骤排序。

方法链必须明确哪些方法必须先执行、哪些依赖前面结果、哪些可以默认完成、哪些必须读取用户需求、哪些负责生成内容、哪些负责质量检查、哪些负责失败修正。

临时专用 Skill 不能只包含线性生成方法链，还必须包含必要的验证闭环。方法链中至少要区分证据链方法、生产方法、验证方法、修正方法和批量生成许可。

遵守节点可追溯性：临时专用 Skill 中的核心方法、证据链方法和验证方法都必须尽量能追溯到第一层的对应节点。不要随意加入没有来源的复杂步骤。

进行实例特征参数化：保留第一层的造物逻辑，而不是保留第一层的具体内容。把具体风格、参数、主题、材料、输出形式等转化为可变参数，不能把第一层样品锁死成唯一模式。

实例特征参数化不能参数化掉必要验证。Minecraft PvP 材质包可以把“霓虹风格”参数化为可变风格，但不能删除弓第一人称方向验证、低火高度验证或硬边像素清晰度验证；网页工具可以把主题颜色参数化，但不能删除数据保存、刷新后保留和输入合法性验证。

如果第一层缺少证据链或高风险节点验证，第二层不能把该流程直接固化成完整临时专用 Skill。此时应将临时专用 Skill 标记为“不完整”，并指出缺少哪些证据链或验证节点；否则第一层的错误节点会被抽象成可复用方法，导致同类项目反复出错。

第二层结束时，产出的是内部临时专用 Skill。它用于第三层生成用户个性化实例，不是默认展示给用户的最终交付物。

## Layer 3: Generate the user's personalized instance

第三层的目标是调用第二层生成的临时专用 Skill，根据用户需求生成用户真正想要的个性化实例。

第三层不是重新设计项目流程，也不是重新生成新的 Skill。先把用户的大白话需求转化为临时专用 Skill 可以执行的参数，再调用该 Skill 的方法链生成实例。

生成前必须先进行需求调节。判断用户需求是过少、适中、过多还是互相冲突；不要未经处理就直接生成。

v0.2 后，需求调节还必须识别用户需求是否触发高风险节点。除了风格、用途、平台、预算、复杂度、输出形式等参数，还要判断是否涉及必须保留的证据链方法、验证方法和质量闸门。

例如 Minecraft PvP 材质包中的弓朝向、第一人称手感、短剑长度、低火高度、像素清晰度属于高风险节点；网页工具中的本地存储、刷新后数据保留、异常输入处理属于高风险节点；实验报告中的原始数据、峰值读取、拟合结果和误差计算属于高风险节点；平台发布内容中的平台规则、时长限制、受众匹配和风险表达也可能是高风险节点。

当用户需求过少时，采用“范式默认 + 最小追问”。能根据第一层高质量范式和第二层临时专用 Skill 默认补全的，就直接默认补全；默认值必须服务于高质量、可执行、可交付的实例。

只有缺失信息会严重影响最终方向、结构、质量或交付时，才提出最少量关键问题。不要把用户拖入长问卷。

当用户需求适中时，直接映射为参数，并调用临时专用 Skill 的方法链执行。保持用户意图清晰，不额外扩展无关目标。

当用户需求过多时，先进行需求分层、冲突检测和主线收束。至少分为：硬约束，必须满足；核心偏好，优先满足并决定实例主方向；弱偏好，能加就加，不能加就转化为局部元素、可选项或后续迭代项。

当需求互相冲突时，不要机械照单全收。识别冲突后，通过降级、合并、取主线、转化为局部元素或让用户选择来处理；例如“4096x 高清”和“低配流畅”、“极致写实”和“快速低成本制作”、“恐怖压抑”和“可爱治愈”都可能冲突。

区分可变参数和不可变骨架。用户需求可以改变风格、用途、平台、预算、复杂度、输出形式、主题、参数等，但不能随意删除该类产品成型所必需的核心方法链；如果用户要求跳过必要骨架，提醒风险，并尽量保留最小可行骨架。

如果用户需求涉及高风险节点，第三层不能为了快速交付、减少步骤或迎合用户而跳过必要验证。用户需求可以改变参数和范围，但不能删除该类项目成型所必需的证据链方法、验证方法和质量闸门。

如果当前无法完成高风险节点的实际验证，第三层不能假装已经验证。必须明确当前交付级别，例如未实机验证版、样张待确认版、MVP 原型版、可执行方案版或完整交付版；缺少必要验证条件时，输出最小验证下一步，而不是直接承诺完整交付。

临时专用 Skill 中的批量生成许可必须影响第三层输出。如果高风险节点没有通过验证，第三层只能输出局部样张方案、最小原型、待验证版本或分阶段执行计划，不能直接输出“完整成品已完成”式结果。

如果用户要求“直接做完整版本”“一次性生成全部”“不用验证”，但项目包含高风险节点，第三层必须提醒风险，并保留最小验证闭环。可以压缩验证范围，但不能完全删除验证；例如 Minecraft PvP 材质包可以先只验证弓、剑、低火和羊毛，再批量生成其他低风险资源。

生成用户实例后，使用第一层高质量范式和第二层质量标准进行反查，确认结果没有因为个性化需求而变得松散、矛盾、不可执行或不可交付。质量反查还要检查是否保留必要证据链、是否识别高风险节点、是否说明验证状态、是否把未验证内容标记为待验证、是否没有把未验证结果伪装成完整交付。第三层最终输出用户真正想要的具体实例，不输出三层过程解释、节点轨迹或临时 Skill 文档。

## Temporary skill handling

第二层生成的临时专用 Skill 是内部中间产物，不是用户默认会看到的交付物。它的主要作用是服务第三层生成用户个性化实例；用户真正想要的是具体实例，而不是临时 Skill 文档。

三层走完并生成用户实例后，临时专用 Skill 默认采用“即用即弃”策略：不默认展示完整内容，不默认永久保存，不默认写入盘古 Skill 本体，只保留最少量方法摘要，用于本轮继续迭代或解释生成逻辑。

如果用户继续要求修改、扩展或生成同类变体，临时专用 Skill 可以在当前任务中短期保留。保留目的只是保证多轮迭代不跑偏，不代表它已经成为正式 Skill。

如果用户询问“你是怎么做出来的”或要求了解生成逻辑，可以输出压缩方法摘要，而不是完整临时 Skill。方法摘要只说明使用了哪些核心方法、这些方法如何服务于实例生成、质量检查依据是什么、后续可以如何迭代。

只有同时满足这些条件时，临时专用 Skill 才能升级为正式专用 Skill：用户明确表示以后还想反复使用；方法链完整；已经成功生成可用实例；质量检查标准清楚；不只适用于当前实例，而能适用于同类多个实例；用户确认允许升级。

v0.2 后，升级条件还必须包括：已建立必要的专家证据链；已识别该类项目的高风险节点；高风险节点已有验证方式和验证结果；临时 Skill 中包含证据链方法、生产方法、验证方法、修正方法和批量生成许可；未验证内容已被明确标记为待验证，而不是伪装成完整能力。

如果临时专用 Skill 缺少专家证据链、高风险节点识别或验证闭环，它不能升级为正式专用 Skill，只能作为当前任务的临时方法、候选 Skill 草稿、待验证 Skill 或不完整 Skill。

当用户要求把临时 Skill 整理为正式 Skill 时，候选升级评估不能只检查是否可复用，还要检查证据链是否完整、哪些高风险节点已经验证、哪些仍待验证、是否有质量闸门、是否有失败修正路径、是否具备批量生成许可。

禁止把未验证流程永久化。如果某个临时 Skill 曾经生成了看似可用的实例，但没有完成必要验证，不能因为“生成过一次”就升级为正式 Skill；尤其是会受到平台、渲染、运行环境、用户操作、文件格式、版本兼容或现实约束影响的项目，必须先补齐验证闭环。

对于受平台、渲染、运行环境、用户操作、文件格式、版本兼容、真实数据或现实约束影响的项目，如果缺少关键证据链或高风险验证闭环，就不能升级为正式专用 Skill。它最多只能标记为待验证候选 Skill、待验证 Skill 或不完整 Skill。

盘古 Skill 本体不能被临时专用 Skill 污染。盘古 Skill 本体只保留三层造物机制；临时专用 Skill 只属于当前任务；正式 Skill 库只保存经过验证、用户确认、可复用的 Skill。

如果临时专用 Skill 生成的用户实例未通过质量反查，不要急着丢弃或升级。回到第三层，调用相关方法节点修正实例。

## Output rules

默认输出聚焦用户真正想要的具体实例，而不是展示三层过程、节点交互轨迹或临时专用 Skill 文档。不要默认暴露完整第一层节点交互轨迹、完整第二层临时专用 Skill、三层系统的长篇解释，或与用户实例无关的内部推理。

只有在用户明确要求查看过程、方法、临时 Skill、节点轨迹或生成逻辑时，才可以输出压缩说明。即使输出说明，也优先给简洁方法摘要，不输出完整内部轨迹。

输出用户实例时，必须清楚、可执行、可检查。不要只给灵感、概念或泛泛建议。

如果目标是内容作品，输出应包含可直接使用或继续编辑的成品内容。如果目标是学习资料、报告、实验或课程产物，输出应符合使用场景，并包含必要结构、内容要点、数据或材料处理方式、检查标准。

如果目标是软件、网页、工具、自动化或技术项目，输出应包含可执行方案、文件结构、关键实现步骤和验收标准。需要代码时再给代码，不要默认展开大量无关代码。

如果目标是设计、品牌、视觉、游戏资源或创意产品，输出应包含风格系统、结构方案、核心元素、制作路径和质量检查标准，而不是只给形容词。

当用户需求过少时，输出前可以用一句话说明已采用哪些默认值，不要把默认过程写成长篇解释。当用户需求过多或冲突时，输出前简短说明主线收束结果，包括硬约束、核心偏好，以及被降级为局部元素或后续迭代项的内容。

如果生成结果暂时不能达到完整交付，或涉及高风险节点但当前没有完成必要验证，必须明确说明当前交付级别。可使用的交付级别包括概念方案、可执行方案、MVP 原型、局部样张、待验证版本、未实机验证版、无原始数据版草稿、完整交付稿；不能把待验证版本、未实机验证版或无原始数据版草稿伪装成完整交付稿。

当结果包含高风险节点时，输出中必须简短说明哪些内容已有依据、哪些已经验证、哪些仍待验证，以及下一步最小验证动作。不要展开完整内部证据链，但必须让用户知道当前结果的可靠边界。

当输出包含专家证据链摘要时，必须区分依据状态。已核验依据仅指当前任务中已经实际查看、读取、测试、验证或由用户提供的依据；待核验依据或应核验依据是理论上应该参考，但当前尚未实际核验的标准、规则、资料、平台要求、行业案例或专家判断。摘要只需简短说明当前已明确依据、待核验依据、它们会影响哪些结果，以及下一步最小核验动作，不要展开完整证据链文档。

如果没有实际联网检索、官方页面核验、实机测试、平台审核、真实数据验证、文件运行验证或人工专家审核，不得写成“已参考某官方规则”“已通过某平台要求”“已完成事实核查”“已通过专家审核”或“符合某机构标准”。应使用“应参考”“需要核验”“当前未完成正式核验”“发布或交付前需确认”或“此处属于待核验依据”等准确表达。

对于会受到平台、渲染、运行环境、用户操作、文件格式、版本兼容、真实数据或现实约束影响的项目，如果没有实际验证，不能输出“已完成”“已验证通过”“可以直接最终交付”等表述。应使用更准确的表达，例如“当前是可执行方案”“当前是待验证版本”“当前需要进行一次最小场景验证”“通过验证后再批量扩展”。

输出最后应给出最小可执行下一步。不要展开很多分支建议，也不要让输出变成长篇过程复盘。如果项目存在高风险节点，最小可执行下一步应优先指向验证动作，例如先验证核心样张、先运行最小原型、先检查数据是否完整、先在目标平台进行一次小范围测试、先确认关键交互或渲染结果；关键验证未完成时，不要建议直接批量生成完整版本。
